chapters/ch02-computer-basics/chapter.html:13:<section id="sec-2-1"><h2>2.1 处理器、寄存器与缓存层次</h2><h3 id="sec-2-1-1">2.1.1 吞吐能力与一条依赖链的等待不同</h3><p>寄存器保存执行指令直接操作的值和地址；指令流水线让取指、译码、执行等不同工作重叠。吞吐量描述一段时间完成多少工作，延迟描述某项工作从开始到结果可用的等待。即使处理器能同时推进多条指令，后续指令依赖前一条结果时，也不能无条件提前使用尚未产生的值。</p><p>分支预测让处理器在条件结果确定前推测下一条路径；预测失败需要放弃不应提交的工作。指令乱序与推测不等于程序可以产生任意结果，架构的可观察行为仍有约束。虚拟机编译器会根据依赖和目标机器选择代码，源文件的行数既不是实际指令数，也不是运行成本的可靠刻度。</p>
chapters/ch02-computer-basics/chapter.html:14:<h3 id="sec-2-1-2">2.1.2 局部性、一致性与伪共享</h3><p>缓存以缓存行为单位保存从更低层存储取得的数据。相邻数据被一起取得，近期使用的数据可能被再次命中，因而顺序访问和重复使用常有局部性收益。共享缓存行在多个核心之间还要满足一致性协议：某个核心的写入可能使其他核心中的相关副本失效或需要协调。</p><p>伪共享发生在逻辑上独立的数据落在同一缓存行中，多个核心写它们时仍竞争这一硬件单位。它不是因为两个变量引用同一 Java 对象才必然发生，也不需要两个线程写同一字段。本机 <code class="shiki-inline" data-shiki-version="4.6.0" data-code-id="code-005" data-code-language="text"><span>sysctl</span></code> 查询的缓存行大小为 128 字节；不能给所有架构固定套上一个常见数字。对象字段的实际排列、对齐和访问模式共同影响结果，本章没有编写压力程序来制造吞吐差异。</p><p>一致性主要约束共享位置或缓存行的数据副本，不直接给所有不同地址提供一套源码顺序。缓存命中也不是 Java 并发语义中的“可见性保证”。后者需要语言及运行时的同步规则，2.5 再接上这一层。[<a href="#s04">S04</a>]</p></section>

chapters/ch08-type-metadata/chapter.html:5:<h3 id="sec-8-1-2">8.1.2 元数据区与堆的关联</h3><p>常规类型及成员元数据由本地元空间管理，堆中的 Class 镜像则由垃圾收集器管理；共享归档等配置还可能使一部分元数据来自映射，不能把所有进程本地内存统称为元空间。Klass 中的 _java_mirror 是句柄，创建镜像的 java_lang_Class::allocate_mirror 又把所代表的 Klass 关联写入镜像。镜像自身的对象类型还是 java.lang.Class 对应的特殊 InstanceMirrorKlass，这与镜像所代表的 Item 元数据是两条不同关系。</p><p>本实现还将类的静态字段存储纳入镜像的相关布局；它不意味着静态字段值都在 C++ InstanceKlass 内，也不等于所有常量都是镜像内的一段字节。第 7 章的常量属性提前填值正发生在镜像建立路径。元数据、对象、对象引用和共享映射要按职责分开，后续内存预算才有清晰口径。</p></section>
chapters/ch08-type-metadata/chapter.html:6:<section id="sec-8-2"><h2>8.2 字段、方法与常量池元数据</h2><h3 id="sec-8-2-1">8.2.1 从文件描述到可执行结构</h3><p>字段在类文件中有名字、描述符和标志；HotSpot 解析后维护编码的字段信息流及查找辅助结构，也确定运行所需的偏移等信息。字段值则在相应实例或静态存储中。反射返回的 Field 对象是 Java 层访问描述，不是那段本地字段信息的原样暴露，更不是字段值本身。</p><p>E01 的 Item 只声明 label，却从 Base 继承 id；getDeclaredFields 的本轮输出因此只有 label。这不能证明实例没有父类字段。字段布局与继承信息需要结合类层次和实现解释，不能通过反射枚举顺序推断物理内存排列。本程序主动按名字排序，仅为输出可读，不表示虚拟机布局顺序。</p><p>方法也不只是一串字节码。InstanceKlass 的 _methods 关联 Method；Method 的 _constMethod 关联 ConstMethod，后者包含常量池关联、代码大小、名字／签名索引以及栈和局部变量等信息，字节码及可选表按其布局保存。Method 同时维护计数、解释与编译入口、可选 nmethod 等运行信息。编译机器码位于代码缓存体系，不应画成“方法的所有东西都在一个元空间块里”。<a href="#s02">S02</a></p>
chapters/ch08-type-metadata/chapter.html:7:<h3 id="sec-8-2-2">8.2.2 符号、运行时常量池与缓存</h3><figure id="fig-8-2"><div class="figure-scroll"><img src="figures/ch08-f02-symbol-mapping.svg" width="960" height="660" alt="类文件名字描述符与代码进入运行时常量池和方法结构，字段和方法解析项分别保存声明者、偏移或方法及调用相关信息，堆中已解析对象通过句柄关联"></div><figcaption>CH08-F02：当前源码的数据关联，不是文件结构逐字复制。索引会重写，不能将 javap 中的原始常量池编号直接当作运行期缓存数组下标。</figcaption></figure><p>类文件常量池是输入格式；运行时 ConstantPool、解析类型数组、ConstantPoolCache 和已解析对象引用构成不同职责的结构。锁定缓存有分别的 ResolvedFieldEntry、ResolvedMethodEntry、ResolvedIndyEntry 数组。字段项保存实际声明者、偏移、原池索引和访问相关标志等；方法项服务方法与调用信息，动态调用项又有自己的关联。</p><p>ResolvedFieldEntry 的源码明确说明字段指令的原常量池索引会被重写为字段项索引。因此文件里的 #N 是某个输入格式的坐标，不是运行时通用指针。字符串等已解析对象仍在堆中，通过句柄关联；缓存名称里出现“常量池”也不意味着对象移入元空间。</p><p>解释执行可以使用这些准备过的项减少重复符号查找，编译器也读取类型、方法和解析信息来生成执行路径。缓存避免重复工作，但不能省去首次所需的访问和加载约束，更不能改变旧字节码遇到不兼容成员应如何报错。这里没有读取本机 C++ 对象地址或每个缓存的动态快照；结构来自锁定源码，Java 输出只证明相应层面的行为。</p></section>

chapters/ch08-type-metadata/chapter.html:15:<h3 id="sec-8-4-2">8.4.2 隐藏与卸载是两个问题</h3><p>本例只指定 NESTMATE，没有指定 STRONG。默认隐藏类可以在定义加载器仍可达时独立具备卸载资格；STRONG 选项则建立与加载器相同的强生命周期关系。即使没有 STRONG，只要某处仍持有 Class、对象或相应调用相关引用，也可能继续维持隐藏类型存活。隐藏不等于“无法通过任何已有引用访问”，更不等于“调用一结束立刻释放”。</p><p>锁定 ClassLoaderData 对非强隐藏类采用镜像持有者，并为其单独的数据记录处理依赖；普通类的记录通常以加载器为持有者。因而一个加载器不必永远只对应一份生命周期数据。E02 只观察定义和调用，不声称测量其卸载时间；下一节用普通短期加载器来观察明确持有关系。</p></section>

chapters/ch12-native-memory/chapter.html:2:<section id="problem"><h2>保留一字节，也能保留八兆内容</h2><p>本章从一个8兆二进制字节（mebibyte，MiB）的直接缓冲区取得1字节切片，随后只保留切片。本轮直接池统计仍显示容量8,388,608字节。切片小，不代表底层拥有的资源也小；与堆中对象图相似，资源账单必须沿持有链追到真实分配。</p><p>技术基线为Java开发工具包（Java Development Kit，JDK）25.0.5.0.2、HotSpot、macOS AArch64。前置为<a href="../ch08-type-metadata/chapter.html">加载器与元数据</a>、<a href="../ch09-runtime-memory/chapter.html">进程账本</a>、<a href="../ch11-allocation/chapter.html">分配和构造</a>。本章并行放入少量加载器、线程与一块显式关闭的外部内存，观察同一进程的三个有界阶段；不主动制造泄漏或资源耗尽。</p></section>
chapters/ch12-native-memory/chapter.html:3:<section id="sec-12-1"><h2>12.1 元空间分配与回收</h2><h3 id="sec-12-1-1">12.1.1 加载器生命期组织元数据分配</h3><p>普通类的元数据与定义加载器生命期关联，类加载器数据（Class Loader Data，CLD）通过ClassLoaderMetaspace组织分配。启用压缩类型指针时，Klass等需要满足编码地址约束的结构与其他元数据使用不同分配空间；这不是把每个Class镜像也搬到类空间。ClassLoaderMetaspace使用适当的MetaspaceArena，后者从共享块管理器取得并管理块，多个类型的小分配可以落在相同分配单元中。</p><p>因此，新增一个类不仅有类本身的数据，还可能引起块申请、对齐、管理结构与共享表变化。工具里的ChunkSz与BlockSz分别代表已分配块容量和块内使用，不能都当作类文件大小，也不能将两者再次相加。非强隐藏类还有第8章说明的独立持有关系，不能简单说一个加载器永远只对应一种卸载单元。<a href="#s01">S01</a></p><figure id="fig-12-1"><div class="figure-scroll"><img src="figures/ch12-f01-metaspace.svg" width="960" height="660" alt="实例与镜像保持加载器关联，加载器数据关联元空间arena与块；卸载后块进入共享管理器，内部复用与页面取消提交是后续不同步骤"></div><figcaption>CH12-F01：元数据分配与回收层次，箭头表示关联或资源归还，不把全部关系当作普通Java强引用。依据S01及第8章持有链。</figcaption></figure>
chapters/ch12-native-memory/chapter.html:4:<h3 id="sec-12-1-2">12.1.2 卸载、复用与归还系统分三步看</h3><p>类型具备卸载条件后，还需收集器执行相应判定和清理。锁定MetaspaceArena析构把所属块交还ChunkManager；后者可合并相邻伙伴块并加入空闲管理结构。到这一层，空间已可被其他元数据分配复用，但仍可能保持提交。另一个回收流程按提交粒度取消提交可释放的空闲块，最终由VirtualSpaceNode调用操作系统接口。</p><p>当前实现的提交粒度与碎片使“释放一份元数据”不必刚好释放一页；稀疏存活的块、共享管理和预留地址又可能形成高水位现象。本轮24个Disposable确有卸载日志，收集事件中的元空间used由1343K降到1310K，提交从1600K降到1536K；释放后本地内存跟踪（Native Memory Tracking，NMT）的Metaspace类别提交仍比初始基线多394KB。新增JDK类、管理结构和统计时点继续影响全局总量，不能用差值倒算这24类的独占占用。</p></section>
chapters/ch12-native-memory/chapter.html:5:<section id="sec-12-2"><h2>12.2 运行时内部内存成本</h2><h3 id="sec-12-2-1">12.2.1 堆之外还有执行和管理的空间</h3><p>平台线程需要本地栈和运行时线程结构；方法编译产生代码缓存内容，编译过程又需要工作空间；符号、模块、句柄、同步结构及服务性工具各有成本。收集器还需要位图、队列及记忆关系等辅助空间。它们与对象的已用堆不是同一个账目，即使没有业务本地库，也不会凭空消失。</p><p>线程数增加可能同时扩大栈预留和已经触碰的页，类数增加可能伴随元数据与解析缓存，编译活动可能产生短峰值和稳定代码占用。不同收集器的辅助结构随堆大小与区域组织变化。不能把各项成本都设成与-Xmx无关的固定常数，也不能把线程栈上限直接乘线程数当作当前驻留。<a href="#s02">S02</a></p>
chapters/ch12-native-memory/chapter.html:6:<h3 id="sec-12-2-2">12.2.2 用活动解释差异，不用差异臆测活动</h3><p>本轮4个教学工作线程在持有阶段确实存在，线程转储显示它们限时停放在同一CountDownLatch。NMT Thread计数比基线多4，栈预留多2048KB，与显式-Xss512k和线程数相符；栈提交增量只有320KB。这里比较的是NMT所跟踪栈，不是4个线程各实际吃满512KB。</p><p>释放后教学线程退出，Java管理接口活线程数从11回到7，但NMT线程计数为19，仍比初始多1，栈预留也没有机械回到旧值。运行时后台活动、观测和分配策略仍可能变化；本章不凭一份差异表指定唯一原因。不同工具统计的“线程数”覆盖范围也不同：Java管理接口与包含运行时线程的NMT不能逐项强行对齐。</p></section>
chapters/ch12-native-memory/chapter.html:7:<section id="sec-12-3"><h2>12.3 直接缓冲区与本地分配</h2><h3 id="sec-12-3-1">12.3.1 包装、视图与拥有者</h3><p>普通堆内缓冲区持有堆数组；直接缓冲区的Java包装对象仍在堆中，内容块可以来自本地分配。锁定Direct-X-Buffer模板的拥有者构造器先调用Bits.reserveMemory，再用Unsafe申请并清零本地空间，登记清理动作；分配或清理登记失败时回退释放。Deallocator记录真正的基址、大小和容量，执行freeMemory并更新Bits计数。</p><p>切片不重新申请同样的底层块。视图构造器根据原缓冲区地址加偏移定位，自己没有独立清理器，att指向拥有者或已有attachment，以免视图还被使用时底层空间提前释放。只留下view.capacity()==1，仍可沿att保持拥有者与完整8MiB资源。<a href="#s03">S03</a></p><figure id="fig-12-2"><div class="figure-scroll"><img src="figures/ch12-f02-ownership.svg" width="960" height="660" alt="长期持有者指向1字节切片，切片attachment保持直接缓冲区拥有者；拥有者关联8MiB本地块和清理动作；Arena另有显式close释放256KiB的路径"></div><figcaption>CH12-F02：本轮资源与释放责任，图中Java对象和本地块分开。切片的强持有与清理登记不是同一种边；依据DirectBuffer模板、Arena契约与O02。</figcaption></figure>
chapters/ch12-native-memory/chapter.html:8:<h3 id="sec-12-3-2">12.3.2 缓存和异步持有会延长整个资源的生命期</h3><p>切片若进入长期缓存，底层块也会随之保留；一个异步操作若还借用这段空间，必须让拥有者在操作完成前存活。释放时既要防止过早使用失效，也要在借用结束后清除不必要持有。Java本地接口（Java Native Interface，JNI）的强引用或本地库自身缓存可能形成额外链条，不能只在Java堆中找一个名为owner的变量。</p><p>Bits的MaxDirectMemorySize约束针对登记的总容量，实际本地申请大小可能因页面对齐不同而变化。管理接口分别给出数量、容量与内存，三个值不应混为一谈；任意本地库的malloc也不自动计入这个直接池上限。本章显式设置上限16MiB，只分配8MiB，未触发限制。</p></section>
chapters/ch12-native-memory/chapter.html:9:<section id="sec-12-4"><h2>12.4 本地内存跟踪</h2><h3 id="sec-12-4-1">12.4.1 同一基线串联三个阶段</h3><p>NMT从启动选择summary或detail。前者给用途汇总，后者增加分配位置等细节；运行时不能把一次没启用的历史申请补成完整跟踪。先记录稳定阶段的baseline，再对同一基线查询summary.diff，才能明确“变化相对于哪里”。锁定NMTDCmd会检查跟踪级别和基线存在，串行执行查询，并把早期与当前MemBaseline交给差异报告器。<a href="#s04">S04</a></p><p>本轮程序的阶段是基线45秒、持有45秒、释放请求后45秒。三次外部快照起止分别为13:20:14—15、13:21:12—13、13:22:04—05，均落在各自程序日志确认的窗口内。首轮15秒窗口曾采晚，原记录保留为不足证据，不拿来替代本轮。</p><div class="table-wrap"><table><caption>CH12-O02同进程各窗口采样；NMT与ps单位均为1024字节，非冻结同步快照</caption><thead><tr><th scope="col">指标</th><th scope="col">基线</th><th scope="col">持有</th><th scope="col">释放后</th></tr></thead><tbody><tr><td>直接池容量，字节</td><td>0</td><td>8388608</td><td>0</td></tr><tr><td>NMT Other提交，KB</td><td>低于显示阈值</td><td>8450</td><td>2</td></tr><tr><td>堆used，K</td><td>3894</td><td>6270</td><td>1797</td></tr><tr><td>ps 驻留集大小（Resident Set Size，RSS），1024字节单位</td><td>56352</td><td>67648</td><td>67712</td></tr><tr><td>vmmap physical footprint，原单位M</td><td>35.0</td><td>39.0</td><td>35.3</td></tr></tbody></table></div><p>持有时8450KB的Other增量与8MiB直接内容、256千二进制字节（kibibyte，KiB）外部块等相符，但类别里还有其他小申请。直接池只覆盖其中8MiB；不能把Other整体命名成“直接内存”。两次diff均相对同一个初始基线，不能把第二次显示的“+2KB”误读为又在8450KB上增加2KB。</p><figure id="fig-12-3"><div class="figure-scroll"><img src="figures/ch12-f03-accounting.svg" width="960" height="540" alt="对象管理统计、NMT用途账和操作系统页账为三个相交但不同的范围；直接池是细分用途，第三方本地申请可能不受NMT覆盖，所有工具都需要阶段和单位"></div><figcaption>CH12-F03：统计范围与证据连接，框不表示可直接相加的集合面积。依据S02—S04与第9章工具手册。</figcaption></figure>
chapters/ch12-native-memory/chapter.html:10:<h3 id="sec-12-4-2">12.4.2 申请账不能替代驻留账</h3><p>NMT跟踪HotSpot路径申请和预留／提交，操作系统工具观察映射、页面和自身的共享归账。HotSpot知道一块空间已释放，不代表底层分配器立刻把相应页面退回系统，也不代表其他区域同时没有增长。本轮Other显著下降而RSS略升，vmmap footprint却下降；这不是靠统一单位就能消除的矛盾，而是范围与口径不同。不能据此宣称已证明某个具体分配器缓存机制，更不能据RSS未降就否定本地释放。</p><p>NMT并不覆盖所有第三方本地分配。堆稳定而RSS增加时，应收集同阶段NMT差异、线程、类与编译活动、直接池、进程映射及本地库自身的分配证据；若NMT解释不了，未覆盖路径就是调查方向之一，而不是立即宣判工具错误。先核对覆盖范围和采样条件，再考虑更具侵入性的本地工具。</p></section>
chapters/ch12-native-memory/chapter.html:11:<section id="sec-12-5"><h2>12.5 释放策略与泄漏</h2><h3 id="sec-12-5-1">12.5.1 关闭、清理与退出提供不同保证</h3><p>本章用线程受限的Arena管理256KiB外部块，在try-with-resources退出时显式close：正常与异常路径都回到资源所有者，成功关闭会结束其内存段生命期。相反，普通allocateDirect包装没有同样的公共close协议；本例只丢弃切片引用，让回收与清理路径接续。本轮确实观察到直接池归零，但“最终可清理”不能写成任意时刻都会及时释放。<a href="#s05">S05</a></p><p>Cleaner提供清理登记与至多一次动作协议，清理状态若反向强持有被登记对象，会阻止自动触发。直接缓冲区的当前实现使用内部清理路径，不能不加说明地等同所有公共Cleaner实现细节；共同要点是持有和触发必须正确。进程退出由系统收回地址空间，不等于应用清理回调总会执行，也不能代替长进程中的及时释放。</p>
chapters/ch12-native-memory/chapter.html:12:<h3 id="sec-12-5-2">12.5.2 按拥有者、持有者与触发点寻找泄漏</h3><p>为每块资源建立三项事实：谁申请并负责释放，哪些对象／线程／本地句柄仍在借用，什么事件触发close或清理。若职责已经结束而某个长期缓存仍保持切片，根因是持有链没有按生命期断开；若所有引用已消失但清理异步尚未执行，则还要研究调度与清理能力，不能把两种情况混称为同一泄漏。</p><p>加载器的文件资源关闭也不代表类型卸载。本例在每次构造实例时就关闭URLClassLoader的文件资源，但保留实例使类型／加载器继续存活；释放实例列表后才在本轮收集中看到24次目标卸载。线程的取消请求与实际退出同样要分开；本例先打开停止闩锁，再有界join，线程自身另有90秒等待上限。第32章将进一步讨论外部内存、回调与本地边界，第35章再以完整故障记录分析泄漏。</p></section>

chapters/ch09-runtime-memory/chapter.html:5:<section id="problem"><h2>只用了几兆堆，进程为何占得更多</h2><p>第 2 章的贯穿程序在一个安静的观察窗口中，堆已用 5594K，进程驻留却为 59248 个 1024 字节单位。程序没有制造泄漏或资源耗尽。这组正常数据已经足以提出问题：堆使用量究竟漏算了什么？本章重新读取那次保存的堆、映射和本地分类记录，不把它冒充一次新运行。</p><p>本书基线为 Java 开发工具包（Java Development Kit，JDK）25.0.5.0.2、HotSpot、macOS AArch64。先掌握<a href="../ch02-computer-basics/chapter.html">进程地址空间</a>及<a href="../ch08-type-metadata/chapter.html">镜像与类型元数据</a>。以下严格区分 Java 虚拟机（Java Virtual Machine，JVM）规范规定的职责、HotSpot 的结构，以及本机实际统计；三者不能直接画等号。</p></section>
chapters/ch09-runtime-memory/chapter.html:6:<section id="sec-9-1"><h2>9.1 规范定义的运行时数据区</h2><h3 id="sec-9-1-1">9.1.1 按共享关系理解职责</h3><p>每个线程有自己的程序计数器和虚拟机栈：前者描述非本地方法当前指令的位置，后者容纳方法帧的局部变量、操作数和调用所需状态。本地方法执行时程序计数器值未定义。实现需要本地方法栈时，通常也随线程提供。线程退出会结束相应线程私有区域的生命期。多个线程共享堆和方法区；每个类型的运行时常量池属于方法区职责，用来表示常量和待解析的符号关系。<a href="#s01">S01</a></p><p>“线程私有”限定的是执行状态归属。局部变量中的引用可以指向共享对象，两个线程也可以在各自栈中保存同一个对象的引用。反过来，一个对象虽然暂时只有一个线程使用，仍可以分配在共享堆里。将引用变量位置与被引用对象位置分开，后续才能理解分配缓冲区和发布。</p><figure id="fig-9-1"><div class="figure-scroll"><img src="figures/ch09-f01-areas.svg" width="960" height="540" alt="左列规范职责分为线程私有执行状态与共享堆方法区，右列 HotSpot 中栈帧、堆对象、元数据与代码有不同物理归属；常量池解析的对象引用跨向堆"></div><figcaption>CH09-F01：规范职责与 HotSpot 承载的对应示意。横向箭头表示职责的承载关系，不表示一对一物理分区。依据 S01、S03。</figcaption></figure>
chapters/ch09-runtime-memory/chapter.html:7:<h3 id="sec-9-1-2">9.1.2 逻辑区域不是一张固定地址表</h3><p>规范不限定所有实现使用同一对象表示、连续分区或收集策略，方法区在逻辑上属于堆，但并不因此等于 HotSpot 的可配置 Java 堆。运行时常量池也不是常量对象的统一物理仓库：元数据中的条目可以通过已解析引用关联堆对象。用“方法区＝元空间”来解释所有内容，会漏掉镜像、静态字段值、已编译代码以及跨区引用。</p><p>因此，规范图适合回答“应保存什么、由谁共享”，进程映射适合回答“哪段地址以何权限映射”，本地分类适合回答“由哪类运行时用途申请”。某工具没有名为“程序计数器”的独立映射，并不表示规范职责缺失；实现可以把相应状态放在线程结构、寄存器或执行帧的表示中。</p></section>
chapters/ch09-runtime-memory/chapter.html:8:<section id="sec-9-2"><h2>9.2 HotSpot 的实际内存组成</h2><h3 id="sec-9-2-1">9.2.1 从用途列账，再看工具</h3><p>Java 堆容纳实际存在的实例和数组。类加载还需要元空间中的类型、方法及常量池元数据；编译器生成的机器代码占代码缓存，编译过程又会产生临时工作空间。线程需要本地栈与运行时线程结构；收集器还需要标记位图、记忆关系及队列等辅助结构。符号表、模块表、句柄、监视器和工具记录也有成本。</p><p>本地内存跟踪（Native Memory Tracking，NMT）按 HotSpot 申请内存时的用途分类，能够显示 Java Heap、Class、Thread、Code、GC 等项；其中垃圾收集（Garbage Collection，GC）辅助结构的成本不能算进对象已用堆。NMT 的计量又不等于操作系统对驻留页的计量。它自身也使用内存，第三方本地库的全部分配并不都在其覆盖范围。<a href="#s02">S02</a></p><div class="table-wrap"><table><caption>复用 CH02-O02 的 NMT 分类摘录，原输出单位 KB，均表示 1024 字节</caption><thead><tr><th scope="col">用途</th><th scope="col">reserved</th><th scope="col">committed</th><th scope="col">解释</th></tr></thead><tbody><tr><td>Java Heap</td><td>139264</td><td>34816</td><td>包含保护前缀，不能直接当作可用对象容量</td></tr><tr><td>Class</td><td>1048685</td><td>301</td><td>含压缩类空间预留及本地小结构</td></tr><tr><td>Metaspace</td><td>65551</td><td>1359</td><td>非类空间等按本工具标签归账</td></tr><tr><td>Thread</td><td>38969</td><td>217</td><td>19 个工具计数线程，预留不等于实际触碰</td></tr><tr><td>Code</td><td>249936</td><td>7920</td><td>代码与相关结构</td></tr><tr><td>GC</td><td>52022</td><td>50166</td><td>收集器辅助成本</td></tr></tbody></table></div><p>这些是特定短进程的分类，不是建议按相同比例预配生产容量。Class 项中额外展示的 Metadata 明细与 Metaspace 主分类存在关联，不能把所有缩进明细再累加一次。保留工具原有层级，才能避免重复计算。</p>
chapters/ch09-runtime-memory/chapter.html:9:<h3 id="sec-9-2-2">9.2.2 静态字段不会让对象进入元空间</h3><p>第 8 章已把 Klass 与 java.lang.Class 镜像分开。锁定实现的 InstanceMirrorKlass::allocate_instance 从 Java 堆分配镜像，instance_size 在镜像基本大小上增加静态字段空间；java_lang_Class::allocate_mirror 再建立镜像与 Klass 的关联。静态字段元数据描述名称、类型和偏移，其值所在的静态字段存储则与堆中镜像关联。静态引用指向的对象仍是堆对象。<a href="#s03">S03</a></p><p>字符串也要拆开：String 对象及其内容数组是堆对象，常量池解析关系和驻留表管理结构承担另外的查找与持有职责。字符串字面量在源码中是常量，不表示它的内容数组位于本地元空间。缓存一个 Class 镜像可能延长加载器与元数据生命期；缓存一个 String 可能保持其内容存活。区域归属与引用持有共同决定账单。</p></section>
chapters/ch09-runtime-memory/chapter.html:10:<section id="sec-9-3"><h2>9.3 预留、提交与驻留</h2><h3 id="sec-9-3-1">9.3.1 地址范围、可用页与当前驻留</h3><p>预留先占据一段虚拟地址范围；提交使其中一部分按操作系统规则成为可用内存。访问页面后是否建立物理驻留，以及之后是否回收、换出或压缩，由系统另行管理。驻留集大小（Resident Set Size，RSS）描述工具口径下当前驻留，不能由预留量直接推导。HotSpot 的 VirtualSpace::expand_by 会按页面粒度提交；commit_expanded 在提交成功后另行判断是否预触碰。实现上这也是两个步骤。</p><figure id="fig-9-2"><div class="figure-scroll"><img src="figures/ch09-f02-budget.svg" width="960" height="660" alt="第一层为虚拟预留，第二层为提交，第三层为驻留并受共享映射影响；下部列出堆、类型、栈、代码、本地资源和余量的进程预算"></div><figcaption>CH09-F02：口径及预算示意，矩形不按比例。提交可用与当前驻留不是同一概念；底部预算是项目容量问题的检查清单。依据 S02—S05。</figcaption></figure><p>本轮收集器报告可用堆预留 131072K，即 128 兆二进制字节（mebibyte，MiB）；NMT 对 Java Heap 报告 139264KB。原映射中另有 8192K 不可访问前缀，两者差异有地址证据，并非堆越过了上限。堆提交 34816K，已用 5594K：这三项甚至都还没有涉及进程的其他区域。</p>
chapters/ch09-runtime-memory/chapter.html:11:<h3 id="sec-9-3-2">9.3.2 共享映射和采集时点也会改变读数</h3><p>本轮 ps 给出 RSS 59248、虚拟大小 490639248，手册规定两者单位均为 1024 字节。vmmap 给出的 physical footprint 是 37.5M，而分区 RESIDENT 总计为 356.1M。共享库、系统共享映射和系统归账方式使这些读数不能互换；不能把 footprint 当成换了单位的 RSS。原记录的 385.0G Guard 区域驻留为零，也直接说明巨大地址范围不等于同量物理消耗。<a href="#s04">S04</a></p><p>采集发生在启动后约 18—20 秒，工具依次附加，不是一次冻结快照。附加、加载、编译和页面回收都可能在间隙继续发生。应比较同一阶段、同一工具、相同单位和选项的连续记录；需要解释差值时再关联事件。尤其不要用“RSS 减去堆已用”声称得到了精确本地泄漏量：堆未用但驻留的页、共享页和采集时差都尚未排除。</p></section>
chapters/ch09-runtime-memory/chapter.html:12:<section id="sec-9-4"><h2>9.4 堆、进程与容器预算</h2><h3 id="sec-9-4-1">9.4.1 把峰值和余量写进预算</h3><p>设对象容量上限为 H，容量规划还需考虑线程栈及线程结构 S、元数据 M、代码和编译活动 C、收集器辅助 G、应用本地资源 N，以及系统映射和运行波动余量 R。H＋S＋M＋C＋G＋N＋R 可作为成本清单，却不是一个能把不同工具值直接相加的精确公式。哪些项随堆规模、线程数或加载类型数变化，必须分别观察。</p><p>例如每增加一个平台线程，栈地址预留和已触碰部分可能不同；动态生成类型会增加元数据与解析结构；编译峰值可能早于稳定业务阶段；直接缓冲区池与本地库则可能在堆稳定时增长。只调低 H 而不减少长期持有者，未必能解决问题；只把 H 调高也可能挤掉本地空间。应在实际资源约束下观察峰值、退出与复用阶段，再确定余量。</p>
chapters/ch09-runtime-memory/chapter.html:13:<h3 id="sec-9-4-2">9.4.2 容器终止与 Java 异常走不同路径</h3><p>Linux 控制组（control group，cgroup）第二版的 memory.max 是组内内存硬限制；到达限制且无法回收时，内核可以在组中选择进程终止。组统计还涉及多个进程和文件等类别，不能直接当成某一个 Java 堆的使用量。容器资源感知可以影响虚拟机的默认容量选择，却不能替应用包办所有本地资源预算。<a href="#s05">S05</a></p><p>Java 分配路径报告 OutOfMemoryError，和内核因内存不足（Out Of Memory，OOM）终止进程，是不同证据链。后者可能来不及生成 Java 异常、堆转储或运行关闭钩子。退出状态只能提示候选原因，还要结合内核／容器事件、memory.events 与限制、进程日志来判断；单独看到 137 不能证明一定是内存终止。本书本轮运行在 macOS，没有容器，也没有主动触发任何终止案例。</p></section>
chapters/ch09-runtime-memory/chapter.html:14:<section id="sec-9-5"><h2>9.5 内存不足与栈溢出</h2><h3 id="sec-9-5-1">9.5.1 从失败的资源种类开始</h3><p>OutOfMemoryError 是一类失败信号，附带信息帮助定位申请路径，不自动等于泄漏。Java heap space 指向对象分配容量；Metaspace 或 Compressed class space 指向相应元数据空间；unable to create native thread 要继续检查系统线程／进程限制、栈及本地空间；直接缓冲区容量限制则有其独立计数与预留逻辑。不同发行版和路径的信息可能变化，应保留完整原因链、版本和有效参数。</p><figure id="fig-9-3"><div class="figure-scroll"><img src="figures/ch09-f03-failure.svg" width="960" height="540" alt="先区分 Java 异常与外部终止；Java 分配失败再按堆、元数据、线程、直接内存分类；每类继续区分上限与持续持有，栈溢出单看调用深度与栈容量"></div><figcaption>CH09-F03：诊断问题树，表示调查顺序，不是本轮故障实测。依据 S01、S03、S05；后续案例由第 35 章承接。</figcaption></figure><p>锁定 Universe 初始化了若干预分配的内存失败对象，包括 Java 堆与元空间等类别，使极端情况下报告错误不必完全依赖新的普通分配。它支持“按路径区分失败”这一机制解释，不代表本章已经触发过这些错误。NMT 未增长也不能排除全部本地库分配，异常中缺少某个关键词也不能替代进程级证据。</p>
chapters/ch09-runtime-memory/chapter.html:15:<h3 id="sec-9-5-2">9.5.2 上限、持有与调用深度分别查</h3><p>容量限制可能过小，短时峰值可能过高，长期持有也可能让回收无法腾出空间。只有区分这些情况，才知道是调整预算、限制并发、关闭资源还是修复持有链。泄漏判断需要生命期依据：对象或本地块在其业务职责结束后仍被不必要地保持，单次使用量高并不足以证明。</p><p>StackOverflowError 则指向线程调用所需栈空间超过允许范围。递归过深、相互递归或过大的帧需求属于候选原因；它与 Java 堆是否有空闲不是同一问题。扩展或新建栈无法取得空间时又可能表现为 OutOfMemoryError。处理之前保留调用栈、线程规模、栈配置和系统限制；提高栈上限会增加多线程预算，不能只看一个线程恢复了运行。</p></section>

chapters/ch10-object-layout/chapter.html:2:<section id="problem"><h2>一个 int，为什么不是四字节对象</h2><p>本章的 SingleInt 只有一个 int 字段，本机默认配置下占 16 字节；显式启用紧凑对象头后仍为 16 字节。空 Object 却从 16 字节降为 8 字节。这两个结果并不矛盾：字段要与头部一起布局，末尾还要满足对象对齐。只有逐项看偏移，才能解释没有节省的原因。</p><p>基线为 Java 开发工具包（Java Development Kit，JDK）25.0.5.0.2、64 位 HotSpot、macOS AArch64；对象对齐为 8 字节，堆上限 128 兆二进制字节（mebibyte，MiB）。Java 虚拟机（Java Virtual Machine，JVM）规范不规定本章的具体字节图，类型元数据与镜像的区别见<a href="../ch08-type-metadata/chapter.html">第 8 章</a>，进程账本见<a href="../ch09-runtime-memory/chapter.html">第 9 章</a>。</p></section>
chapters/ch10-object-layout/chapter.html:3:<section id="sec-10-1"><h2>10.1 普通对象与数组的组成</h2><h3 id="sec-10-1-1">10.1.1 先找最后一个字节，再向对齐边界取整</h3><p>传统 64 位头部包含状态字与类型信息。本轮开启压缩类型指针，状态字 8 字节、类型字 4 字节，普通字段可从偏移 12 开始。SingleInt.number 恰好占 12—15，得到 16 字节；空 Object 没有字段，需要把 12 字节头部向 8 字节边界取整，产生 4 字节末尾填充。若实际关闭类型压缩，头部组成又会改变，不能把 12 字节叫作所有配置的固定对象头。</p><p>估算时先确定字段实际偏移与宽度，取最大结束位置，再按对象对齐向上取整。数组另有 4 字节长度，其元素起始还取决于元素类型对齐。可以写作 size＝alignUp(base＋length×scale, alignment)，其中 base 是该元素类型的实际起始偏移，scale 是元素宽度；不能拿一个数组的 base 套所有数组。空数组即使没有元素，也有头部、长度和必要填充。<a href="#s01">S01</a></p><figure id="fig-10-1"><div class="figure-scroll"><img src="figures/ch10-f01-layout.svg" width="960" height="680" alt="默认单整数对象由8字节状态字4字节类型和4字节字段构成16字节；紧凑模式头8字段4末尾填充4仍16；字节数组和长整数数组的起始对齐不同"></div><figcaption>CH10-F01：以本轮偏移和大小绘制的布局对照，不按图形宽度计字节。依据 O01、oopDesc／arrayOopDesc；普通字段重排另见 10.1.2。</figcaption></figure>
chapters/ch10-object-layout/chapter.html:4:<h3 id="sec-10-1-2">10.1.2 字段顺序、继承空洞与对象图</h3><p>源码先声明 long sequence、再声明 byte tag，并不承诺它们按这个顺序紧贴排列。本轮传统布局中 Base.tag 位于 12，Base.sequence 位于 16；紧凑布局中 sequence 位于 8，tag 位于 16。FieldLayoutBuilder 会按宽度与引用组组织字段，依据父类布局、空洞及引用映射等安排；它必须保留父类字段的已定偏移，却不必把整个父类对象的尾部填充也当作不可利用字段。</p><p>本轮 Child 在传统模式的 count／reference 位于 24／28，紧凑模式位于 20／24，最终两者都占 32 字节。布局移动了，取整后总大小未变。静态字段属于第 9 章讨论的镜像关联存储，不重复计入每个 Child 实例。<a href="#s02">S02</a></p><p>对象自身大小又称浅大小，只算当前实例的字节。Mixed.reference 指向一个 byte[10]，数组成本不包含在 Mixed 的 24 字节中。两个 Mixed 共用该数组时，可达图只计数组一次。本轮工具遍历得到三对象，传统布局共 80 字节，紧凑布局共 72 字节；这不是任一对象独占的保留大小。与其他根共享的对象不能简单按某个引用分摊。</p></section>
chapters/ch10-object-layout/chapter.html:5:<section id="sec-10-2"><h2>10.2 对象头中的运行时信息</h2><h3 id="sec-10-2-1">10.2.1 类型、哈希、年龄与同步各有职责</h3><p>类型定位使运行时能找到对象所属 Klass，进而取得大小、引用字段映射和方法等结构。身份哈希服务 System.identityHashCode 语义，不能当作稳定地址或唯一标识；对象移动后还要保持相应语义。年龄位可供特定收集过程使用，不代表对象已存活多少秒。锁相关位帮助同步路径判定当前表示，也不独立保存全部等待线程。</p><p>锁定 markWord.hpp 的 64 位普通状态字从高位向低位包含未用位、31 位身份哈希、4 位保留间隔、4 位年龄、1 位自转发和2位锁标记。紧凑模式把高处原本未用的 22 位用于压缩类型信息。这个布局中的 hash_shift 是 11；它与旧版图中的位移不同。位宽来自当前源码，不能从第三方工具的旧术语反推。<a href="#s03">S03</a></p>

chapters/ch10-object-layout/chapter.html:7:<section id="sec-10-3"><h2>10.3 两类压缩指针</h2><h3 id="sec-10-3-1">10.3.1 对象引用与类型指针压缩不同的目标</h3><p>压缩对象引用针对堆中对象地址，常见目标是缩小引用字段与引用数组元素；压缩类型指针针对本地 Klass 地址，减少对象头的类型表示。它们有不同地址范围、基址和配置，不能把 UseCompressedOops 与 UseCompressedClassPointers 当作同一开关。紧凑对象头要求压缩类型信息，不意味着概念上必须把所有对象引用也压成同一种位宽。</p><p>锁定 CompressedOops::decode 对零值单独返回空引用；非零值经过 base＋(unsigned(narrow)＜＜shift) 解码。编码反向减去基址并右移，前提是地址满足对齐与范围。CompressedKlassPointers 有独立基址和位移，公式相似但不共享全部数值。读取紧凑头时还要先从状态字提取压缩类型位。<a href="#s05">S05</a></p><figure id="fig-10-2"><div class="figure-scroll"><img src="figures/ch10-f02-decode.svg" width="960" height="560" alt="压缩对象引用先判零，非零按对象堆基址加左移结果解码；压缩类型信息使用另一基址和位移，紧凑头须先提取22位类型编码"></div><figcaption>CH10-F02：两种编码的独立解码关系；表示公式，不是对本机某个对象地址的猜测。依据 CompressedOops、CompressedKlassPointers、markWord。</figcaption></figure>
chapters/ch10-object-layout/chapter.html:8:<h3 id="sec-10-3-2">10.3.2 地址范围、对齐和可表示空间一起决定配置</h3><p>32 位窄对象引用配合 3 位左移时，编码空间可覆盖约 2³⁵ 字节的地址跨度；这是一种常见推算，不等于所有配置都能在任何地址预留同样大小堆。零值保留、保护范围、堆基址、收集器限制和实际地址布局也参与选择。调整对象对齐可能换取更多可表示跨度，却会给大量小对象增加尾部填充。只背“超过某容量就一定关闭压缩”不足以解释实际配置。</p><p>本轮两主进程的 HotSpot 日志均报告 Zero based、oop shift amount 3；工具的引用元素宽度均为 4。Java Object Layout（JOL）未附加服务性代理（Serviceability Agent，SA），它自己打印的基址／位移有明确猜测警告，不能据此声称本机类型指针也恰好按相同位移解码。对象引用模式以虚拟机日志为准，类型编码的机制以锁定源码为准；本章不伪造具体 Klass 地址。</p></section>

chapters/ch11-allocation/chapter.html:4:<h3 id="sec-11-1-2">11.1.2 解释器与编译代码不必经过同一条调用链</h3><p>解释器可以在模板中完成类型检查与分配快路径，不能每次都画成先进入一个公共 C++ 函数。编译后代码则可能把空间检查、指针推进和必要初始化展开为机器指令；失败分支才调用运行时辅助入口。C2 的 PhaseMacroExpand::expand_allocate_common 负责展开分配节点，内含缓冲区空间与慢调用路径。若节点已经被消除，就没有这次常规分配展开。</p><p>快路径失败也不等于立即触发回收。剩余缓冲区太小、当前对象不适合放入缓冲区、需要补充缓冲区、堆分配失败等具有不同处理。将慢路径与回收画等号，会漏掉正常的缓冲区外分配，也难以解释“堆还有空间却发生辅助调用”。编译模式、内联边界和收集器都要随记录注明。<a href="#s02">S02</a></p></section>
chapters/ch11-allocation/chapter.html:5:<section id="sec-11-2"><h2>11.2 线程本地分配缓冲区</h2><h3 id="sec-11-2-1">11.2.1 线程独占分配游标，不独占对象语义</h3><p>线程本地分配缓冲区（Thread-Local Allocation Buffer，TLAB）是从堆取得的一段可由当前线程推进游标的分配区。ThreadLocalAllocBuffer::allocate 读取 top，比较 end与top之间剩余空间，足够时把top增加对象大小。每个线程各自推进自己的游标，从而减少每个小对象分配时对共享分配游标的协调；取得新缓冲区仍须与堆分配器协作。</p><p>缓冲区属于某个线程的分配过程，里面的对象仍在Java堆，可被安全发布给其他线程。TLAB既不是线程栈，也不是安全发布机制。对象从哪里分配，与之后由谁持有、是否逃逸，是两个维度。escapedSum把刚分配的Pair发布后，并不需要把它从“私有内存”复制到另一块共享堆。</p><figure id="fig-11-2"><div class="figure-scroll"><img src="figures/ch11-f02-tlab.svg" width="960" height="540" alt="线程A和B在共享堆中有独立TLAB，各自推进top；对象不合适时保留旧缓冲区走外部分配，或退休旧区并申请新缓冲区；对象可被发布"></div><figcaption>CH11-F02：分配所有权与对象共享分开表示，空间不按比例。依据MemAllocator与ThreadLocalAllocBuffer，不代表每个线程具有相同大小缓冲区。</figcaption></figure>
chapters/ch11-allocation/chapter.html:6:<h3 id="sec-11-2-2">11.2.2 剩余空间决定保留还是补充</h3><p>慢路径先处理采样可能缩短的end边界，再检查剩余空间与refill_waste_limit。剩余较大时，可能保留旧TLAB，让当前对象走缓冲区外分配，以免丢掉过多空间；剩余较小时，记录浪费、退休旧区并计算新大小。申请新缓冲区可能获得最小和期望之间的大小，也可能失败后转向共享堆接口。缓冲区退休时还需使残余空间符合堆可遍历要求。</p><p>本轮gc+tlab日志确有fill、refills、slow allocs与waste；飞行记录器（JDK Flight Recorder，JFR）也记录了分配新TLAB时的Pair，以及一个准备阶段的缓冲区外Pair。事件中的tlabSize是整块缓冲区大小，allocationSize是触发事件的对象大小，不是每个对象都独占一块同样大的缓冲区。不同事件覆盖方式不同，不能把某个“新TLAB事件”计数当作对象总数。<a href="#s07">S07</a></p></section>
chapters/ch11-allocation/chapter.html:7:<section id="sec-11-3"><h2>11.3 对象初始化与安全发布</h2><h3 id="sec-11-3-1">11.3.1 默认值、头部与构造器完成不同职责</h3><p>对象字段首先具有语言规定的默认值，实例字段初始化和构造器再建立用户期望状态。实现可以在获取整段缓冲区时清零，也可以逐对象完成必要清零，甚至在证明语义等价时消掉冗余写入。本基线ObjAllocator::initialize调用mem_clear与finish；mem_clear清理对象数据并处理类字间隙，finish设置状态及类型信息。</p><p>finish使用release写入，使清零、数组长度与头部状态在“对象可被并发收集器解析”的边界前建立。紧凑头写prototype_header，传统布局设置mark再发布klass。这个内部协议不等于Java代码已经执行完构造器。随后调用的&lt;init&gt;还可能写字段、调用父类构造器或抛异常。第5、7章核对的灵活构造器前导语句规则也没有删除默认初始化和安全发布要求。<a href="#s03">S03</a></p>
chapters/ch11-allocation/chapter.html:8:<h3 id="sec-11-3-2">11.3.2 有引用、构造完成与其他线程可见分别判断</h3><p>运行时为收集器识别对象，不会自动使其他Java线程以正确同步关系读到业务字段。Pair构造完再写publishedPair，volatile写与随后读到相应发布的volatile读建立先行发生关系；第25章将完整展开Java内存模型（Java Memory Model，JMM）的动作推理。本章没有通过并发跑几次来替代规范依据。</p><p>final字段具有专门的初始化安全语义，但它不把对象变成深度不可变，也不修复构造期间错误泄露this的设计。构造器正常返回说明当前创建过程完成；对象被其他线程取得，还需分析发布方式与可见关系。单次运行里打印出了期望值，不足以证明缺少同步的程序正确。<a href="#s03">S03</a></p></section>
chapters/ch11-allocation/chapter.html:9:<section id="sec-11-4"><h2>11.4 字段、数组与字符串访问</h2><h3 id="sec-11-4-1">11.4.1 字段偏移和数组步长建立地址联系</h3><p>对象引用经当前编码解码后，字段访问依据已解析字段的偏移定位，继承字段的实际偏移由布局决定。数组元素的概念地址为对象起始加base与index×scale，还要满足空引用和边界等语义要求；检查可能由编译器合并或在已证明安全的范围内消除，但不能改变允许的行为。引用字段／元素的读写还可能带收集器屏障，并非任何配置下都只有一次普通机器加载或存储。</p><p>第10章实际记录了int[]与long[]在紧凑头下不同的base。拿这些偏移理解访问时仍须保留类型、配置与移动可能性，不能把某次读出的地址当作长期不变的对象身份。Java源码中的getfield、putfield或数组指令也不是完整机器码时序。</p>
chapters/ch11-allocation/chapter.html:10:<h3 id="sec-11-4-2">11.4.2 内容共享、驻留与去重是三种关系</h3><p>锁定String使用byte[] value和byte coder；紧凑字符串允许适合的内容采用Latin-1，其他内容采用Unicode转换格式16位（Unicode Transformation Format 16，UTF-16）表示。对外的char索引语义不随内部编码改变。本轮只读反射看到“memo”的coder为0，“内存”为1；这是当前实现和配置，不是允许应用长期依赖的字段接口。</p><p>String(String original)直接复用原value与coder，所以复制构造可以得到不同String对象却共用内容数组。由相同字符数组分别构造则会复制内容，本轮开始时两个包装对象及内容都不同。intern返回规范化的String引用，不会把已有变量自动改写：first.intern()==separate.intern()为true，first与separate仍是两个对象。<a href="#s04">S04</a></p><p>垃圾收集（Garbage Collection，GC）字符串去重处理的是可共享的内容数组。锁定StringDedup::Table找到相同内容后，经允许性检查及锁保护替换String的value引用，保留包装对象身份。本轮保留4000个独立构造的128字符字符串：关闭去重时，两次有界回收请求后的内容数组身份数仍4000；启用去重、年龄阈值1时，第一次请求后的观察已变为1，第二次仍1。独立事件日志还记录了并发去重工作。<a href="#s05">S05</a></p><p>日志总计4074次初轮去重包含其他字符串，不能全归给这4000个样本。请求回收也不保证指定时刻去重完成；本轮各等0.5秒后观察只是实际结果。去重不会让字符串的==变成值相等，也不会自动消除缓存中的包装对象。读取内部value需要本次命令显式开放java.lang，仅用于只读教学观察。</p></section>

chapters/ch11-allocation/chapter.html:21:<h3 id="sec-11-5-2">11.5.2 去优化可能重新需要一个真实对象</h3><p>标量替换后，逻辑上仍需保持对象、字段与身份相关语义。优化代码在安全点保留恢复所需描述；去优化需要还原可观察状态时，Deoptimization::realloc_objects按类型建立对象，reassign_fields把恢复值写回，并处理多个描述之间的引用与别名关系。恢复不是重新执行用户构造器，否则可能重复业务副作用。</p><p>所以“源程序有对象但当前无对应堆分配”与“必要时物化”可以同时成立。它不意味着把一个完整普通对象永久搬到线程栈，也不证明所有不逃逸对象都栈上分配。本章只研究恢复实现，没有制造去优化事件；详细状态重建和失败处理由第18章承接。<a href="#s06">S06</a></p></section>

chapters/ch11-allocation/chapter.html:23:<section id="review"><h2>回顾与思考</h2><p>分配是空间取得与表示建立，构造是业务状态初始化，发布是跨观察者的同步关系，回收则取决于持有和收集协作。优化可以改变物理表示，却必须维持这些操作的可观察语义。</p><ol><li>为什么TLAB外分配不一定引发GC？为什么TLAB对象可以被另一线程使用？</li><li>运行时设置klass的release写入，与把引用写入volatile字段，分别服务谁的可见协议？</li><li>为什么同一方法在准备阶段能出现分配事件，稍后又能观察到分配消除？</li><li>字符串去重后，还能用==比较任意字符串内容吗？为什么驻留又是不同的操作？</li></ol><p>第12章将沿离开Java堆的资源继续追问：谁拥有空间，谁只持有一个视图，以及何时真正释放。</p></section>
